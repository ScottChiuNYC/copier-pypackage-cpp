# Project Skeleton Contract

Contract version: 1.1

## 1. Purpose

This document is the normative development contract for the reusable C++/Python project skeleton generated by `copier-pypackage-cpp`.

It tells developers and AI agents **where implementation belongs and how it connects to the repository's build, packaging, dependency, binding, test, and CI machinery**. It is intentionally domain-agnostic.

A domain implementation specification such as `essence.md` describes **what must be implemented**. This contract describes **how that implementation fits into this repository skeleton**. Read both before implementation work.

The project-local copy of this file is authoritative for a generated project. If that project intentionally changes a skeleton convention, update this contract in the same change.

## 2. Ownership boundary

The project skeleton owns:

- repository layout and source locations;
- C++ and Python build integration;
- pybind11 extension placement;
- dependency declaration and wiring;
- packaging and native-extension build mechanics;
- C++ and Python test integration;
- build presets and supported developer build flows;
- CI entry points.

A domain implementation specification owns:

- logical components and public behavior;
- domain APIs and data contracts;
- algorithms and numerical methods;
- supported and unsupported product/model scope;
- domain validation and acceptance criteria;
- which third-party capabilities are required.

A domain specification may require a library such as Tasmanian or Eigen, but it should not redefine repository paths, package layout, dependency plumbing, or build mechanics unless changing the skeleton itself is part of the task.

## 3. Repository layout

The standard generated layout is:

```text
project root
├── CMakeLists.txt
├── CMakePresets.json
├── build.py
├── pyproject.toml
├── vcpkg.json
├── vcpkg-configuration.json
├── cpp/
│   ├── CMakeLists.txt
│   ├── include/
│   │   └── <module>_core/
│   ├── src/
│   └── bindings/
├── src/
│   └── <module>/
├── tests/
│   ├── cpp/
│   └── python/
├── examples/
│   └── cpp/
└── docs/
    └── development/
```

Here `<module>` is the generated Python module name.

### 3.1 C++ public headers

Public C++ headers belong under `cpp/include/<module>_core/`.

Headers consumed by another C++ target or by bindings belong under this public include root rather than beside implementation files.

### 3.2 C++ implementation

Production C++ implementation belongs under `cpp/src/`.

The baseline `cpp/CMakeLists.txt` recursively discovers `cpp/src/**/*.cpp` (including top-level sources) with `GLOB_RECURSE CONFIGURE_DEPENDS`. Nested C++ implementation directories require no CMake source-list changes. If implementation introduces a different target decomposition, update CMake explicitly. Keep unrelated `.cpp` files outside `cpp/src/`.

### 3.3 Python bindings

pybind11 binding translation units belong under `cpp/bindings/`.

If bindings are split across multiple translation units, update `cpp/CMakeLists.txt` so every required source is compiled into the extension. Bindings adapt the C++ public interface to Python; do not duplicate domain algorithms in binding glue.

### 3.4 Python package

Pure Python implementation, exports, type helpers, calibration/research code, and Python-facing orchestration belong under `src/<module>/`.

The compiled extension is emitted directly into this package directory so development tests and built wheels use the same package namespace.

### 3.5 Tests and examples

C++ GoogleTest sources belong under `tests/cpp/`. Python pytest sources belong under `tests/python/`. Standalone C++ examples belong under `examples/cpp/`.

The baseline C++ test CMake file discovers top-level `tests/cpp/*.cpp`. If tests are reorganized into nested directories or multiple executables, update CMake explicitly.

Domain specifications own **what must be tested**. This skeleton owns **where tests live and how they are registered**. Examples are not substitutes for tests.

## 4. CMake contract

The root `CMakeLists.txt` establishes the language standard, enables CTest, and delegates to implementation, examples, and tests.

The baseline C++ layer provides:

- a static C++ core library built from `cpp/src/`;
- public include access through `cpp/include/`;
- a pybind11 extension linked to the C++ core library;
- direct extension output into `src/<module>/`.

When expanding the project:

- prefer target-based CMake;
- attach include directories with `target_include_directories`;
- attach dependencies with `target_link_libraries`;
- attach compile definitions/options to the target that owns them;
- preserve dependency direction from reusable core code toward adapters and bindings, not the reverse;
- do not place domain logic in root build files.

If a new logical component needs a new CMake target, the domain specification may require that logical separation, while this contract governs how the target is wired into the repository.

## 5. C++ dependencies

vcpkg is the standard C++ dependency manager.

For a normal new C++ dependency:

1. add it to `vcpkg.json`;
2. follow the project's existing registry and overlay policy in `vcpkg-configuration.json` and any repository-local port directories;
3. use the package's CMake config from the narrowest appropriate CMake layer, normally with `find_package(... CONFIG REQUIRED)`;
4. link its imported target only to the CMake target that needs it;
5. validate on the supported platforms.

Do not change a recorded vcpkg baseline merely to add a normal dependency. A baseline, registry, or package-provider migration is a skeleton-level change and must be treated explicitly.

The baseline skeleton manages pybind11 through CMake `FetchContent`. Do not silently introduce a second pybind11 installation path. Moving pybind11 to another provider is a skeleton-level migration and must update build files and this contract together.

Repository-local overlay ports should be used only when the standard dependency source is insufficient or intentionally overridden.

## 6. Python dependencies

Python runtime dependencies belong in `[tool.poetry.dependencies]`. Development-only dependencies belong in the appropriate Poetry development group, currently `[tool.poetry.group.dev.dependencies]`.

Keep runtime and development dependencies separate. A dependency change that affects build or tests must be validated through the corresponding Poetry, CMake, and test paths.

## 7. Packaging contract

Poetry is the Python packaging frontend and `poetry.core.masonry.api` is the build backend. `[tool.poetry.build]` invokes `build.py`, and `build.py` configures/builds the native extension with the project CMake presets before Poetry completes packaging.

The native extension is emitted into `src/<module>/`, and wheel include rules package the resulting `.pyd` or `.so` beside the Python sources.

The source distribution must contain **every input required to rebuild the native extension from the unpacked sdist**, not only C++ source files. Keep the `pyproject.toml` sdist include rules aligned with the executable build graph. Required inputs include, as applicable:

- root `CMakeLists.txt`, `CMakePresets.json`, and `build.py`;
- `vcpkg.json` and `vcpkg-configuration.json`;
- repository-local overlay/port files referenced by the vcpkg configuration;
- every nested `CMakeLists.txt` traversed during configure;
- C++ headers, implementation, and binding sources;
- example or test CMake/source files when the selected packaging configure path includes those subdirectories;
- any additional generated/configuration inputs required by CMake.

If source, header, binding, CMake, test, example, or dependency-layout paths change, update the sdist include rules in the same change.

A packaging change is complete only when the intended clean artifact can import the package without relying on accidental files from the original source checkout. If the project claims wheel-from-sdist support, validate that path from an unpacked sdist rather than inferring it from a source-checkout build.

### 7.1 Independent C++ package

The CMake package version uses the numeric release component of the Poetry version; prerelease/build metadata remains in Poetry and the port manifest. The static core also installs as a CMake package `<module>_core` with target `<module>_core::core`. `BUILD_PYTHON_BINDINGS=OFF` excludes Python discovery, pybind11 FetchContent and the extension. `BUILD_EXAMPLES=OFF` and `BUILD_TESTING=OFF` exclude development targets for packaging. Default presets keep those existing targets enabled.

CMake installs the core library, public headers, and config/version/export files using separate build/install include paths. `cmake/LibraryConfig.cmake.in` is a native configure input and must be included in the sdist. The local library overlay under `vcpkg-ports/` has its own port manifest, separate from the root development dependency manifest. It stays inside the source checkout and always packages the core statically, with CRT linkage determined by the triplet.

`scripts/validate_vcpkg.py` installs this port into an independent consumer, relocates the installed prefix, hides source headers, checks imported paths, and compiles/links/runs Debug and Release. Keep `tests/vcpkg-consumer/` aligned with the public API when changing the example API. The normal validation invokes it after existing C++/Python and wheel validation. See the generated README for exact install and consumer commands.

## 8. Canonical developer build and test flows

For fresh environments, run:

```bash
python scripts/bootstrap.py
python scripts/validate.py --wheel
```

These scripts supply the pinned tools, vcpkg checkout and Ninja path for nested vcpkg processes and the parent Linux configure. `scripts/validate.py` runs `poetry install --no-root`, CMake configure/build, CTest and pytest with the freshly built module on `PYTHONPATH`; `--wheel` also rebuilds a native wheel from the sdist and checks clean installation.

| Platform | Configure preset | Build preset | Test preset |
| --- | --- | --- | --- |
| Windows | `windows-vcpkg` | `windows-release` | `windows-release-tests` |
| Linux | `linux-vcpkg-release` | `linux-release` | `linux-release-tests` |

For package validation, `poetry build` must continue to invoke the native build through `build.py`.

Keep tool-path setup in `scripts/bootstrap.py` and canonical build/test sequencing in `scripts/validate.py`; the CMake/Poetry build remains authoritative.

## 9. CMake presets

`CMakePresets.json` is the canonical location for supported configure, build, and test presets.

When adding a platform, toolchain, or build mode, extend the preset model instead of creating an unrelated parallel build path. `build.py`, documentation, local workflows, and CI must agree on preset names and semantics.

Do not commit environment-specific absolute paths into shared presets unless they are intentionally part of the project contract.

## 10. CI contract

The generated `.github/workflows/build-and-test.yml` is the baseline CI entry point. It validates Release build, CTest, and pytest on the supported Windows and Linux configurations when relevant implementation, dependency, build-system, or test files change.

Domain specifications define correctness criteria; CI defines how those criteria are exercised automatically. Add substantive validation to the appropriate C++ or Python test suite rather than embedding domain logic in workflow YAML.

Changes to build, dependency, packaging, or CI machinery must pass the repository's normal PR checks. Template-level changes should additionally validate a freshly generated sample project.

## 11. Interface with domain implementation specifications

A domain implementation document should state logical requirements, for example:

```text
Required implementation units
- discount curve
- swaption product
- SABR--Cheyette model
- pricing engine
- Python calibration layer
- Python bindings for the public pricing API
- C++ and Python acceptance tests
- Tasmanian as a required C++ capability
```

The implementation agent maps those logical requirements through this contract:

```text
C++ public interface   -> cpp/include/<module>_core/
C++ implementation    -> cpp/src/
Python binding glue    -> cpp/bindings/
Python implementation -> src/<module>/
C++ tests              -> tests/cpp/
Python tests           -> tests/python/
C++ dependency         -> vcpkg manifest/config + target-level CMake wiring
Python dependency      -> pyproject.toml
```

The domain specification should not repeat these physical paths or build instructions. Conversely, this contract should not contain domain algorithms, product semantics, model formulas, calibration policy, or numerical acceptance criteria.

## 12. Skeleton evolution

Treat the skeleton as shared infrastructure.

A normal domain implementation may add source, bindings, dependencies, tests, and logical targets through the extension points above. It should not redesign build or package architecture incidentally.

If a task genuinely changes a skeleton convention, update all affected pieces together:

- this contract;
- build/package/dependency files;
- README or onboarding references;
- CI where applicable;
- the Copier template when the change should apply to future projects.

Do not allow the executable skeleton and the written contract to drift apart.

## 13. Independent overlays and review publication

This Project Skeleton Contract is authoritative for the generated project's build, package, dependency, layout, and test conventions. It does not make this template the owner of unrelated overlays.

A project may independently apply ART. When both templates are present:

- `.copier-answers.pypackage-cpp.yml` records this skeleton's provenance;
- `.copier-answers.art.yml` records ART provenance;
- ART owns its generated `AGENTS.md`, CodeBinder publication skill/workflow, and `.codebinderignore.d/art`;
- this template owns `.codebinderignore.d/pypackage-cpp`;
- an optional root `.codebinderignore` remains project-owned.

The CodeBinder fragment is a **review presentation policy**, not build authority. It may hide CMake/vcpkg/packaging/editor plumbing from the review PDF while those files remain fully authoritative for actual builds. Do not infer that an ignored PDF file is unused by the project.

Do not merge owner-specific ignore fragments into one shared generated file. Composable fragments exist so independent templates can evolve without creating Copier ownership conflicts.

For the full cross-repository dependency and rollout model, see:

https://github.com/ScottChiuNYC/agentic-repo-template/blob/main/docs/ecosystem-architecture.md

## 14. Developer/agent checklist

Before implementing a domain feature:

- read this contract and the domain implementation specification;
- classify each required component as C++, bindings, Python, tests, or dependency work;
- place each component in the skeleton-owned location;
- wire dependencies through the existing package/build mechanisms;
- update CMake and sdist rules whenever new paths require them;
- install the Poetry development environment before `poetry run` commands;
- run the relevant C++ and Python tests;
- validate packaging when bindings, native build inputs, or package structure change;
- keep infrastructure conventions out of the domain specification unless infrastructure itself is changing.

The reconstruction rule is:

> **Project Skeleton Contract + domain implementation specification + referenced mathematical/domain specifications must be sufficient for a fresh developer or AI agent to implement the in-scope functionality without inventing repository-layout, build, dependency, packaging, or test conventions.**

## 13. Coding standards (non-formatting policy)

The canonical external references are the [Google C++ Style Guide](https://google.github.io/styleguide/cppguide.html) and [Python PEP 8](https://peps.python.org/pep-0008/). Use them for **new or materially edited code** (including declarations, tests, examples, bindings, and client code), subject to the existing repository APIs and the following project-specific precedence:

- For C++, use Google conventions for naming, 2-space indentation, include ordering, braces and comments; maintain clear mathematical alignment where it improves readability. Python-exposed names follow PEP 8, even when bound to C++ PascalCase functions.
- For Python, use PEP 8 (4-space indentation, snake_case functions, CapWords classes, organized imports). Preserve intentionally readable mathematical layouts.
- Existing C++ `.cpp` files, the `hello()` sample API, C++17 baseline, and existing exception semantics are **compatibility decisions**, not invitations to silently rename sources, break clients, raise the language version, or change error handling. Existing code is grandfathered until an explicitly scoped change; new filenames should follow the project's established build and packaging conventions. A future `.cc` migration must update CMake discovery, packaging, consumers and tests together.
- Preserve intentionally aligned mathematical tables, matrices and coefficient definitions; readability and local context take precedence over mechanical reflow.
- **Do not run auto-formatters or introduce formatting-only CI gates.** Tools such as clang-format or Ruff format are optional, manually invoked aids only, never mandatory or applied repo-wide by an agent. Non-mutating lint reports may assist focused review but are not blanket approval gates.
- Review *changed lines* for reasonable compliance. Never make a drive-by mass-reformatting commit, especially while propagating Copier updates. If style conflicts with a frozen public interface or domain requirement, preserve behavior and document/escalate the conflict rather than silently change the contract.

These conventions are Project Boundary mechanics: ICC includes them when producing illustrative code or interface declarations without repeating them in each Essence; C2C applies them to generated implementations, acceptance tests and reviews. Domain acceptance criteria remain independent of cosmetic formatting.
